所有策划和开发文档统一放在这里。

                 ┌──────────┐
                 │   剧情   │
                 │ 故事/情绪 │
                 └────┬─────┘
                      │
                剧情需求 / 内容
                      ↓
                 ┌──────────┐
                 │   关卡   │

                 └────┬─────┘

剧情定义“为什么发生、发生什么” → 关卡定义“玩家怎么经历它” → 技术定义“怎么实现” → 美术定义“看起来是什么”

但这里有一个关键例外：

剧情可以直接向技术提出“需求”，但不应该直接规定技术实现。

例如剧情写：

女儿拿起黄色雨伞后进入童年记忆。

这是剧情需求。

关卡再把它翻译成：

玩家靠近雨伞 → 出现交互 → 点击后触发记忆场景 → Camera 转场 → 玩家控制权恢复。

技术看到的是这个。

剧情不要写：

“技术使用 SceneManager 切换 Scene，然后调用 xxx API。”

这会把职责搞乱。

`narrative/`

- 故事
- 角色
- 对白
- 情绪曲线

## 关卡

`level-design/`

负责：

- Demo Flow
- 关卡流程
- 交互
- 谜题
- Trigger

## 美术

`art-bible/`

负责：

- 视觉风格
- 色彩
- 人物比例
- 牵挂线视觉规范
- AI 出图规范

## 技术

`technical/`

负责：

- Godot 技术架构
- 开发规范
- 核心机制实现说明

剧情组应该交什么

剧情组不要写一份“巨长剧情文档”就结束。

你们这次只有几天，我建议剧情组只交 4 份核心文档。

01｜剧情总纲

这是所有人的共同基础。

文件：

/docs/story/01_story_overview.md

只回答：

游戏讲什么？

包括：

故事一句话
核心主题
母女关系
世界观最低限度说明
角色介绍
起承转合
最终情绪落点
核心意象：牵挂线、雨伞等

不要写几十页。

1～3 页足够。

02｜剧情流程 / Story Flow

这是给关卡策划看的。

文件：

/docs/story/02_story_flow.md

重点写：

段落	剧情发生什么	玩家应该感受到什么	新信息
开场	母女同行	熟悉、温暖	母女关系
第一次牵挂	女儿看到线	好奇	线存在
第一次分离	女儿走远	紧张	线有张力
雨伞	进入记忆	怀旧	过去存在
结尾	女儿走远	释然	关系不会断

这里不要规定关卡怎么设计。

剧情只告诉关卡：

玩家在这里必须经历什么。

03｜剧情对白表

这个直接给关卡 + 技术 + 美术。

文件：

/docs/story/03_dialogue.md

推荐字段：

ID	触发条件	角色	台词	情绪	是否阻塞流程
D001	开场	妈妈	……	温柔	否
D002	首次看到牵挂线	女儿	……	惊讶	否
D003	雨伞交互	女儿	……	怀念	是

这里的 ID 非常重要。

技术以后可以直接：

D001
D002
D003

实现。

剧情改台词，只改这个表。

04｜剧情需求单

这个是剧情和其他组的接口。

文件：

/docs/story/04_story_requirements.md

比如：

SR-001

需求

玩家第一次看到牵挂线时，需要明确意识到它是特殊机制。

发生位置

第一次母女分开。

目标

让玩家理解“距离会产生牵挂”。

关卡需要

安排一次足够明显的母女距离变化。

美术需要

牵挂线第一次出现需要突出表现。

技术需要

触发一次线出现的演出。

这就是很重要的：

剧情提出需求，但不决定怎么实现。

三、关卡组应该是整个团队的“中间层”

这个岗位最关键。

因为关卡要把：

翻译成：

然后再翻译成：

所以关卡组建议至少交 5 份文档。

03｜关卡设计文档

这是给策划自己和技术看的。

/docs/level/03_level_design.md

每个谜题按照：

P001｜母女距离

目标

让玩家理解牵挂线的张力。

玩家行为

女儿远离妈妈。

系统反馈

线逐渐拉紧。

成功条件

玩家返回安全距离。

失败条件

没有真正失败，只产生拉回演出。

剧情意义

第一次理解母女之间的牵挂。

美术表现

线颜色、粗细、动画。

技术需求

距离检测、Line2D、张力状态、触发动画。

这就是一个真正好用的关卡文档。

五、剧情需要直接对接技术吗？
需要，但只在“内容需求”和“触发需求”层面。

你们可以规定：

剧情可以提出技术需求，但不得规定技术实现方案。

例如剧情：

SR-004 女儿进入雨伞记忆后，需要暂时失去现实世界控制权。

可以。

技术自己决定：

Lock Input
Change State
Camera Transition

怎么实现。

六、反过来技术也不能直接找剧情要“你写个故事”

技术应该给：

实现限制 / 技术能力

例如：

TECH-008 目前无法实现实时动态绳索物理。

然后关卡和剧情调整成：

使用距离 + Line2D + 状态切换。

这才是正确的协作。

你们的实际工作流应该变成这样

举个你们现在的黄色雨伞。

剧情

写：

女儿看到黄色雨伞，想起童年与妈妈一起避雨的经历。

↓

关卡

翻译成：

玩家靠近黄色雨伞 → 出现交互 → 触发记忆 → Camera 演出 → 进入童年场景。

↓

关卡 → 技术

提出：

需要 Interaction、Camera Transition、World State、Dialogue Trigger。

↓

关卡 → 美术

提出：

需要黄色雨伞、当前客厅、童年客厅、记忆转场素材。

↓

技术

实现：

Interaction + State + Camera + Dialogue。

↓

美术

制作：

PNG / Sprite / Animation。

↓

关卡

最后把：

剧情 + 技术 + 美术

装成一个可玩的关卡。

所以关卡其实是你们三组之间的“编译器”。

剧情说人话。

关卡把人话编译成玩家行为。

技术把玩家行为编译成程序。

美术把玩家行为编译成视觉。

这个结构非常适合你们现在这种三天极限开发。
