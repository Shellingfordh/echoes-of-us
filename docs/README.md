# 项目文档

所有策划和开发文档统一放在 `docs/` 下。

```text
                 ┌──────────┐
                 │   剧情   │
                 │ 故事 / 情绪 │
                 └────┬─────┘
                      │
                剧情需求 / 内容
                      ↓
                 ┌──────────┐
                 │   关卡   │
                 │玩法 / 流程 / 体验│
                 └────┬─────┘
                      │
          ┌───────────┴───────────┐
          ↓                       ↓
     技术实现需求              美术制作需求
          ↓                       ↓
       ┌───────┐               ┌───────┐
       │  技术  │               │  美术  │
       └───────┘               └───────┘
```

整体流程：

> **剧情定义“为什么发生、发生什么” → 关卡定义“玩家怎么经历它” → 技术定义“怎么实现” → 美术定义“看起来是什么”。**

剧情可以直接向技术提出需求，但不要规定技术怎么实现。

例如剧情写：

> 女儿拿起黄色雨伞后进入童年记忆。

这是剧情需求。

关卡再把它翻译成：

> 玩家靠近雨伞 → 出现交互 → 点击后触发记忆场景 → Camera 转场 → 玩家控制权恢复。

技术看到的是这个。

剧情不要写：

> 使用 SceneManager 切换 Scene，然后调用某个 API。

具体怎么实现由技术决定。

# 一、剧情 `narrative/`

负责：

* 故事
* 角色
* 对白
* 情绪曲线
* 剧情需求

剧情组这次不需要写很长的世界观，重点是让关卡知道玩家在什么时候应该经历什么。

## 01｜剧情总纲

文件：

`docs/narrative/01_剧情总纲.md`

这是所有人的共同基础。

主要写：

* 故事一句话
* 核心主题
* 母女关系
* 必要的世界观说明
* 角色介绍
* 故事起承转合
* 最终情绪落点
* 核心意象，例如牵挂线、黄色雨伞等

控制在 1～3 页，不要写成小说。

---

## 02｜剧情流程

文件：

`docs/narrative/02_剧情流程.md`

主要给关卡使用。

重点写每个剧情段落：

| 段落    | 剧情发生什么 | 玩家应该感受到什么 | 新信息   |
| ----- | ------ | --------- | ----- |
| 开场    | 母女同行   | 熟悉、温暖     | 母女关系  |
| 第一次牵挂 | 女儿看到线  | 好奇        | 线存在   |
| 第一次分离 | 女儿走远   | 紧张        | 线有张力  |
| 黄色雨伞  | 进入记忆   | 怀旧        | 过去存在  |
| 结尾    | 女儿走远   | 释然        | 关系不会断 |

这里不要规定具体关卡怎么做。

剧情只需要告诉关卡：

> **这一段玩家必须经历什么，以及为什么要经历。**

---

## 03｜剧情对白表

文件：

`docs/narrative/03_剧情对白表.md`

给关卡、技术、美术共同使用。

建议格式：

| ID   | 触发条件    | 角色 | 台词 | 情绪 | 是否阻塞流程 |
| ---- | ------- | -- | -- | -- | ------ |
| D001 | 开场      | 妈妈 | …… | 温柔 | 否      |
| D002 | 首次看到牵挂线 | 女儿 | …… | 惊讶 | 否      |
| D003 | 黄色雨伞交互  | 女儿 | …… | 怀念 | 是      |

对白 ID 要固定。

技术实现时可以直接对应：

```text
D001
D002
D003
```

以后修改台词，只改对白表，不要让技术到处找台词。

---

## 04｜剧情需求

文件：

`docs/narrative/04_剧情需求.md`

这是剧情和其他组的接口。

例如：

### SR-001｜第一次出现牵挂线

**需求**

玩家第一次看到牵挂线时，需要明确意识到它是一个特殊机制。

**发生位置**

第一次母女分开。

**目标**

让玩家理解“距离会产生牵挂”。

**关卡需要**

安排一次足够明显的母女距离变化。

**美术需要**

牵挂线第一次出现时需要有明显的视觉表现。

**技术需要**

支持牵挂线出现的触发和演出。

这里剧情负责提出需求，不负责决定技术和关卡具体怎么实现。

---

# 二、关卡 `level-design/`

关卡是整个团队的中间层。

主要负责把：

> **剧情发生什么**

转换成：

> **玩家做什么**

再转换成：

> **技术需要实现什么、美术需要制作什么。**

关卡组需要维护 5 份文档。

---

## 01｜关卡总览

文件：

`docs/level-design/01_关卡总览.md`

回答：

> 这一关玩家到底经历什么？

例如：

### Level 01｜不断线

**目标**

让玩家理解牵挂线的基础规则。

**流程**

```text
母女同行
→ 女儿离开
→ 发现牵挂线
→ 线产生张力
→ 玩家学习控制距离
→ 遇到锚点
→ 完成第一次解谜
→ 黄色雨伞
→ 进入记忆
→ Ending
```

---

## 02｜关卡流程

文件：

`docs/level-design/02_关卡流程.md`

这是技术最重要的文档之一。

建议直接把整个流程写出来：

```text
Start
 ↓
D001
 ↓
玩家移动
 ↓
T001
 ↓
牵挂线出现
 ↓
玩家教学
 ↓
P001
 ↓
谜题完成
 ↓
T002
 ↓
黄色雨伞交互
 ↓
M001
 ↓
Ending
```

所有需要技术识别的节点都给 ID。

例如：

```text
T001 = 第一次看到牵挂线
P001 = 第一个牵挂谜题
T002 = 黄色雨伞触发
M001 = 第一次记忆
```

这样技术不需要从长篇剧情里自己找触发点。

---

## 03｜关卡设计

文件：

`docs/level-design/03_关卡设计.md`

具体描述玩家怎么玩。

每个谜题按照下面的格式写。

### P001｜母女距离

**目标**

让玩家理解牵挂线的张力。

**玩家行为**

女儿远离妈妈。

**系统反馈**

线逐渐拉紧。

**成功条件**

玩家返回安全距离。

**失败条件**

没有真正失败，只产生拉回演出。

**剧情意义**

第一次理解母女之间的牵挂。

**美术表现**

描述需要什么视觉效果，例如线条变化、角色动画、镜头变化。

**技术需求**

描述需要什么能力，例如距离检测、牵挂线状态、触发动画。

这里写的是**需求**，不要写具体代码。

---

## 04｜关卡技术需求

文件：

`docs/level-design/04_关卡技术需求.md`

这个文件专门给技术。

只写：

> **技术需要提供什么能力。**

不要直接写代码实现方案。

例如：

### TECH-001｜牵挂线

需要支持：

```text
起点
终点
最大距离
当前距离
```

需要至少存在：

```text
Normal
Tension
Broken
```

三种状态。

具体使用什么节点、脚本和代码结构由技术决定。

---

### TECH-002｜交互

需要支持：

> 玩家进入物品附近后可以触发交互。

---

### TECH-003｜记忆转场

需要支持：

> 触发记忆 → 暂停玩家控制 → Camera 转场 → 切换场景状态 → 播放对白 → 恢复玩家控制。

---

## 05｜关卡美术需求

文件：

`docs/level-design/05_关卡美术需求.md`

这个文件专门给美术。

例如：

### ART-001｜家庭客厅

需要：

* 背景
* 地面
* 沙发
* 桌子
* 窗户
* 黄色雨伞
* 相框

### ART-002｜牵挂线

需要：

* 普通状态
* 张力状态
* 连接状态

### ART-003｜记忆转场

需要：

* 当前空间
* 童年空间
* 两个空间叠加过渡所需素材

美术拿到这个应该就能直接开始做，不需要自己猜“到底要画什么”。

# 三、美术 `art-bible/`

美术负责：

* 视觉风格
* 色彩
* 人物
* 场景
* 道具
* 牵挂线视觉表现
* AI 出图
* 最终素材交付

美术不要只提交 PNG，规范和资产信息也要一起维护。

---

## 01｜美术规范

文件：

`docs/art-bible/01_美术规范.md`

这是整个美术组最高优先级的文档。

包括：

* 视觉风格
* 镜头视角
* 色彩
* 光影
* 人物比例
* 场景比例
* 线条风格
* UI 风格
* 牵挂线视觉规范
* AI 生成规范
* 禁止事项

后面所有 AI 生成的东西都按照这里统一。

---

## 02｜角色设定

文件：

`docs/art-bible/02_角色设定.md`

例如：

| ID   | 角色 | 年龄阶段 | 外观 | 服装 | 色彩 | 备注 |
| ---- | -- | ---- | -- | -- | -- | -- |
| C001 | 女儿 | 成年   | …  | …  | …  | 主角 |
| C002 | 女儿 | 童年   | …  | …  | …  | 回忆 |
| C003 | 母亲 | 年轻   | …  | …  | …  | 回忆 |

剧情需要新增角色或者改变角色设定时，先更新剧情，再同步美术。

## 04｜素材交付规范

文件：

`docs/art-bible/04_素材交付规范.md`

规定美术最终交给技术的文件格式和命名。

例如：

```text
ENV_L01_ROOM_BG.png
ENV_L01_SOFA.png
CHR_DAUGHTER_ADULT_IDLE.png
CHR_DAUGHTER_ADULT_WALK.png
PROP_YELLOW_UMBRELLA.png
```

需要统一规定：

* 文件格式
* 是否透明背景
* 图片尺寸
* Pivot
* 锚点
* 分层
* Sprite 切割方式
* 动画素材格式
* 文件命名

目标很简单：

> **技术拿到素材就能用，不需要再问美术这是什么。**

# 四、技术 `technical/`

技术组负责：

* Godot 技术架构
* 核心机制实现
* 系统实现说明
* 开发规范
* 技术限制

但三天项目里技术文档不要写太多。

技术最重要的是：

> **先把核心玩法跑起来。**

技术可以维护一个简单的：

`docs/technical/README.md`

里面记录：

```text
当前技术方案
核心系统
现有可复用组件
实现限制
使用方式
已知问题
```

例如目前确认：

```text
引擎：Godot 4
角色：CharacterBody2D
牵挂线：Line2D
交互：Area2D
镜头：Camera2D
```

具体代码结构由技术自己决定。

---

# 五、剧情和技术怎么对接

可以直接对接，但只对接**需求**。

剧情负责：

> “女儿进入黄色雨伞的记忆后，暂时无法控制现实中的角色。”

关卡负责：

> “玩家交互黄色雨伞 → 触发 M001 → 锁定控制 → Camera 转场 → 进入记忆场景。”

技术负责：

> “用什么状态管理、节点、Scene、Signal、Camera 实现。”

所以：

> **剧情提出内容需求 → 关卡整理成玩家行为 → 技术决定实现方式。**

---

# 六、技术也不能反过来要求剧情决定实现

例如技术发现：

> 目前无法实现实时动态绳索物理。

技术应该告诉关卡：

> 当前技术限制是无法做实时绳索物理。

然后关卡调整：

> 使用距离检测 + Line2D + 状态切换。

剧情只需要确认：

> 最终玩家是否还能获得“牵挂产生张力”的体验。

不要让剧情策划去解决技术问题。

---

# 七、实际工作流

以黄色雨伞为例。

### 剧情

> 女儿看到黄色雨伞，想起童年与妈妈一起避雨的经历。

↓

### 关卡

> 玩家靠近黄色雨伞 → 出现交互 → 触发记忆 → Camera 演出 → 进入童年场景。

↓

### 关卡 → 技术

> 需要 Interaction、Camera Transition、World State、Dialogue Trigger。

↓

### 关卡 → 美术

> 需要黄色雨伞、当前客厅、童年客厅、记忆转场素材。

↓

### 技术

> 实现交互、状态、镜头和对白触发。

↓

### 美术

> 制作 PNG、Sprite、Animation 等素材。

↓

### 关卡

> 把剧情、技术和美术组合成可玩的关卡。

所以可以简单理解成：

> **剧情说发生什么，关卡决定玩家怎么经历，技术决定怎么实现，美术决定怎么呈现。**

这就是这次项目所有人的基本协作规则。
